Not present: tests that send a request through the security filter chain and the `@PreAuthorize` checks (the controller tests are standalone `MockMvc` over mocked services), a coverage tool (JaCoCo is not configured), performance or load tests, React component tests (the Vitest suite covers plain functions, not rendered components).

## 2. Running the tests

```bash
# Backend — needs JDK 25 and the database container (docker compose up -d postgres mailpit)
cd backend && ./mvnw test            # PowerShell: .\mvnw.cmd test

# Frontend: static checks and unit tests (no stack needed)
cd frontend && npm run lint && npm test && npm run build

# End-to-end — needs the FULL stack running and the Chromium browser installed once
docker compose up -d --build
cd frontend && npx playwright install chromium && npm run test:e2e
```

**In CI** (`.github/workflows/ci.yml`, every pull request into `dev` or `main`): the `frontend` job runs lint, `npm test` and the build; the `backend` job loads the schema, checks that every migration is folded into the init scripts (`database/check_migrations_folded.sh`: Flyway runs against the database just built and must have nothing to apply), checks the database invariants, creates the application role with `03-app-role.sh`, checks that the role can read every table (`database/verify_grants.sql`) and runs `mvn -B verify`; the `e2e` job (after those two) makes `backend/logs` writable for the container's unprivileged user, runs `docker compose up -d --build --wait` on the clean runner so the init scripts seed an empty database, installs Chromium and runs `npm run test:e2e` with 2 workers and 2 retries, uploading the Playwright report and printing the service logs if anything fails. That job was validated by running the same steps on a second copy of the stack (a Compose override with other ports and container names, and the CORS origin set for the new port); it has **not yet been seen running on GitHub**.

More detail and troubleshooting: [setup.md](setup.md#6-running-the-tests).

## 5. Database tests

`database/verify_invariants.sql` runs fifteen read-only queries that must return no rows: tasks without dates; active tasks with an incomplete dependency; assignees who are not project members; assignees who are not `ACTIVE`; tasks linked to another project's milestone; stale project progress; stale milestone progress; a project without exactly one active owner; an owner who cannot own projects; a pending approval request on a task that is not in review; a task in review without an open request; a project whose completion date disagrees with its status (`V14`); a project lead who is not an active Team Leader of the project (`V15`); a COMPLETED task with no subtasks or checklist items that is not at 100 (`V17`). CI executes it right after loading the `database/init/*.sql` scripts and fails on any output. It checks that **the data is consistent**, not that each trigger *rejects* a bad write — there are no tests that attempt a violating `INSERT`/`UPDATE` and expect an error.
