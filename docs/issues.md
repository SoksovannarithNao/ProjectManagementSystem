# Bug & Issue Tracking

A register of what is wrong, what was fixed, what is planned and what is intentionally limited. It was compiled on **2026-10-06** from the code, the running application, the git history (79 commits), existing READMEs and TODO markers. There is no issue tracker file in the repository (`.github/agents/issue-triager.agent.md` describes an automated triage helper, but no issue list is stored in the repo), so **GitHub Issues, if used, were not available to this scan** — items there are **Unknown**.

Evidence tags: **verified live** (reproduced against the running stack) · **by code reading** (not run) · **needs verification**.

Severity: **High** = breaks a stated security or data-isolation requirement · **Medium** = wrong behaviour or notable exposure with limited reach · **Low** = polish, hardening, or documentation.

## 8. Known limitations (accepted or by design)

- **Paging is optional and only on the project, task and notification lists**; every other list endpoint reads everything. No screen reads the whole task list any more (F-71, F-75, F-80, F-81, F-82), but the task assignments and the project members are still read whole by the screens that need them (the task form, Team and the project pages). Full-replace `PUT`, no `PATCH`.
- **Stateless JWT access tokens**: a token cannot be recalled before it expires (15 minutes; refused at once if the account stops being `ACTIVE`). The refresh cookie (7 days) is deleted on sign-out and on a password change, and is not rotated on use; the browser signs itself out after 15 idle minutes; no forgot-password flow.
- **The hosted app runs on free tiers (2026-10-17):** Render stops an idle backend, so the first request afterwards can take 30 to 60 seconds, and Render's free tier blocks outgoing SMTP, which is why hosted mail uses the Gmail API ([host/README.md](../host/README.md)).
- **Google sign-in and sign-up (2026-10-24):** connecting an *existing* account needs its password, so a person who forgot it (there is no forgot-password flow) cannot connect Google until an administrator resets it, and a Google account is never matched to an account by e-mail. Anyone with a Google account that has a verified e-mail can create a `USER` account (no wider than `/register`); someone who edits their own profile e-mail to another person's address stops that person creating an account with Google (they are told to sign in and connect), which captures nothing. A Google-created account has no password until it sets one, so switching Google sign-in off strands it until an administrator resets its password. There is no `nonce` on the ID token, connecting and disconnecting are not in the audit log (its `action` list is a `CHECK`; creating an account is, as `ACCOUNT_CREATED`), and connecting does not count wrong passwords toward a lock-out, as for changing a password. The Google Cloud Console origins must list each site exactly (`https://www.task-flow.lat`, `http://localhost:5173`): Vercel preview URLs do not work. By hand on 2026-10-24, connecting a real Google account, signing in with it and creating an account from a second one worked; setting that account's first password with a real Google account is not yet confirmed ([google-sign-in.md](google-sign-in.md), [ADR-0017](adr/0017-link-only-google-sign-in.md), [ADR-0018](adr/0018-google-sign-up-and-first-password.md)).
- **The Gmail refresh token can stop working:** it is revoked by a password change on the Gmail account or by removing the app under the Google account's third-party access, and it expires after 7 days if the Google Cloud OAuth app is left in *Testing*. Sends then fail with `503` until a new token is made.
- **The administrator's sign-in code needs a real mailbox:** with `ADMIN_2FA_ENABLED=true` and an unreadable administrator address nobody can sign in as the administrator; the way out is to remove the setting and redeploy.
- **The hosted demo accounts share a public password** (the seed password is in the repository), so the hosted administrator's password must be changed after the first sign-in.

- **In-memory login limiter** (reset on restart, not shared across instances).
- **No live updates:** data and notifications refresh on load and after the user's own actions.
- **Unassigning a task notifies nobody.** The specification lists no such notification, and a new type would need a schema change; the person simply no longer sees the task. (Adding one is in D-10's open question about member changes.)
- **A project can be marked Completed with unfinished tasks:** the brief asks only that the status reflect the real state, so a manager may close a project early; no rule forbids it.
- **`kpi_snapshots` and `report_exports` have no code behind them:** the KPIs and reports are calculated on demand and exported in the browser, so the unique key of `kpi_snapshots` (its NULL project is not de-duplicated) has no effect.
- **Single task assignee in the UI** although the API supports several.
- **Authorization is data, with a fixed catalog:** an administrator edits which role holds which permission on which resource and can add extra system roles (G-06, built 2026-10-13), but a new resource or action needs a code change and a migration.
- **A database cannot be built from the migrations alone:** `V1` to `V23` on an empty server fails at `V13`, because the task/subtask consistency functions and triggers exist only in the init scripts (tested 2026-10-14, X-04). Use the supported routes: a fresh volume from `database/init/`, an older one baselined at 8 and upgraded by `V9` onward.
- **Flyway is not run by the application;** the init SQL is the schema for a fresh volume and Compose's one-shot `migrate` service applies later migrations.
- **Notifications:** all 12 types are produced (none for a member added or removed, which D-10 leaves pending). Deadline and overdue notices are sent once, by a daily job at 08:00 and at startup: nothing is sent between runs, and a reminder day missed while the backend was down is not made up.
- **Reports:** the KPIs and the seven named reports are calculated on the server; the *Overview* charts are still computed in the browser, except the Workload chart, which shows the server's workload figures (2026-10-13); each can be saved as an Excel or PDF file, made in the browser (2026-10-13); the PDF uses a standard Latin font, so a character outside it may not print.
- **Profile photos and attachments live in the database** (portable, but they bloat the `users` and `attachment_contents` tables and every backup; at most 10 MB x 25 files per task or project).
- **Uploads are not virus-scanned and the upload endpoint has no rate limit of its own** (it needs a signed-in member with `ATTACHMENT:CREATE`; size, count and type are limited). A scanner and a per-user upload limit are the next hardening steps.
- **Seed data and development secrets** are for development only.
- **Responsive layout** was audited at 390, 768, 1024 and 1360 px on 2026-10-08; no later audit is recorded for the screens added since (approvals, reports, timeline, team views).
- **Each e2e run leaves a few `activity_logs` rows** (task created/deleted, subtask added/deleted for tasks the tests create and delete). They are detached from any task (`task_id` NULL) so no screen or endpoint shows them; there is no API to remove activity entries.

## 9. Technical debt

| Item | Why it matters |
|---|---|
| Services fetch the caller's project ids and filter in memory (`TaskService.getAllTasks`, `MilestoneService.getAllMilestones`, `TaskDependencyService.getAllTaskDependencies`) | Fine for the demo dataset; unbounded and un-paged as data grows. `MilestoneService` and `TaskDependencyService` load **all** rows then filter |
| `updateX` methods apply request-body relations (`projectId`, `userId`) after checking permission on the *old* relation | Root cause of the former I-03/I-05; now guarded in `TaskService`, `MilestoneService` and `ProjectMemberService`, but any **new** update endpoint that accepts a relation id must re-check the target |
| Two schema sources (`init/*.sql` and Flyway) maintained by hand | Already drifted (X-04) |
| Frontend still loads two whole collections, `/api/task-assignees` (the task form, Team and the project pages) and `/api/project-members`, and derives views from them client-side; every task list has been read from the server since 2026-10-14 | Small relation tables, unbounded in principle: they would need the same treatment as the task lists if an organisation grew very large |
| No automated tests for most services, controllers, triggers and screens | See [testing.md](testing.md#8-missing-or-weak-coverage) |
| `User.profilePhoto` is an eagerly loaded `byte[]` column, so every `User` entity load (also when nested via members, assignees, projects) reads up to 5 MB of photo | Likely heavy for list endpoints as photos accumulate (by code reading; not measured) |
| `spring.jpa.show-sql=true` in the default configuration | Noisy production logs |
| `PUT /api/users/{id}` has no uniqueness pre-check (the database refuses it and the answer is now a plain sentence, `That username is already taken.`) | I-11, fixed 2026-10-14 |
| Dev defaults for passwords and the JWT secret in `docker-compose.yml`/`.env.example` | A warning is logged for the JWT secret only |
